## Pi.NET 与 Microsoft Agent Framework (.NET) 全面对比

产出报告：`output/pi-net-vs-agent-framework.md`（含架构、模块、选型、扩展性、性能、选型打分与建议）。

- **实测口径**：pi.net 17 个 src 项目（13 发布）、266,903 行、14 个测试项目、4,974 个 Fact/Theory、仅 net10.0、4 个第三方包；
  MAF 35 个跟踪项目（10 个 GA）、133,881 行、48 个测试项目、7,241 个测试特性、5 个 TFM、135 个中央包版本、53 份 ADR。
- **核心判断**：两者只在「LLM 调用 + 工具循环 + 会话」约 3k 行处重叠；Pi.NET 纵深（编码 Agent + TUI + 42 provider），
  MAF 广度（superstep 图编排 + 检查点 + A2A/AG-UI/OpenAI 托管 + OTel/Purview）。MAF 的循环实际下沉到
  `Microsoft.Extensions.AI` 的 `FunctionInvokingChatClient`，`ChatClientAgent` 只是适配器——这是最本质差异。
- **Pi.NET 短板（可执行）**：测试默认不进 CI 门禁（`continue-on-error`）、发布包未开 XML 文档、无 OTel 适配器、
  无 A2A/OpenAI 兼容出口、无 AOT/多目标、TS 扩展不可加载、上游仍有 88 提交待消化。
- **MAF 风险**：`AzureAI`/`DurableTask`/`AGUI`/`Hosting.AzureFunctions` 源码已不在主干（迁独立仓库），
  本快照只剩 bin/obj，跟版本需读 release notes；135 个包含多个 beta/preview，供应链成本高。
- **建议**：企业平台以 MAF 为控制面、Pi.NET 为执行面/参考实现，用 A2A 或 MCP 做进程边界，不做代码级缝合。

## 扩展系统：进程内加载 TS/JS（方案 A，commit 568daa7）

用户决定"完全兼容上游 TS 插件，用方案 A"，落地进程内 JavaScript 宿主，扩展不再只认 .dll。

- **新增代码**：`src/Pi.CodingAgent/Core/Extensions/Js/`（`TypeScriptTranspiler`、`JsExtensionRuntime`、
  `JsExtensionHost`、`JsExtensionModuleLoader` + `CompositeExtensionModuleLoader`、`ExtensionRuntimeAssets`）；
  资产 `Assets/extension-runtime/`（`vendor/babel.min.js` 3MB、`prelude.js`、`shims/*.js`）。
- **关键机制**：Babel standalone 跑在 Jint（`sourceType: unambiguous` 统一 TS/ESM/CJS，内容哈希缓存，
  **编译线程 64MB 栈**——TypeBox 生成式解析器会爆默认栈）；CommonJS 模块系统 + node_modules 解析；
  每个扩展一个 engine；JSON 桥（`__piHost.call(method, argsJson)`）；Promise 泵 =
  `Engine.Advanced.ProcessTasks()` + 自建 timer 队列；跨扩展 `pi.events` 用静态订阅表按 host 分发。
- **验证口径**：`JsExtensionTests` 6 例全绿；扩展相关 147 例通过；`dotnet build Pi.slnx` 0 警告。
  上游 86 个 TS 示例一次性探针：**73 个加载并注册成功**；6 个无默认导出（辅助模块，非失败）；
  7 个失败 = 4 个缺第三方 npm 包（@anthropic-ai/sdk、gondolin、sandbox-runtime、ms）+ 2 个
  provider/virtual-model 注册 + 1 个读 ~/.pi/extensions/auth.json 的测试脚本。
- **语义分档（重要）**：渲染器注册（message/entry/tool/markdown）降级为警告，扩展照常加载；
  provider / virtual-model 注册显式抛错（避免误判已注册）；`ctx.ui.custom()` 抛错（需同进程渲染循环）。
- **待办**：① 组件协议桥（render(width)→string[]，可解锁 ui.custom 与三个 renderer）；
  ② provider 注册（需 streaming 协议）；③ `JsComponent` 让工具/消息用 JS 渲染；
  ④ 编译缓存落盘（当前仅进程内缓存，冷启动首译 ~2s 加载 Babel）；
  ⑤ `create*ToolDefinition` 目前 schema 宽松（`additionalProperties: true`），执行走 ctx.executeTool。

### 运行期审查（commit 6e27d1c）：修掉 6 个缺陷，通过率 55 → 71/86

用 `ExtensionRunner` 真实派发事件后，暴露的问题（上一版「加载即注册」的验证口径抓不到）：

1. **`api.on` 没做 ctx 转换**：宿主传原始 JSON 给 handler，`ctx.ui.notify` / `ctx.sessionManager.getBranch`
   / `ctx.ui.theme` 全是普通字段 → 18 个上游示例在 `session_start` 崩溃。修法是 prelude 里包一层
   `__pi_make_context`。**这是影响面最大的一个**。
2. **`pi.*` 工厂返回后失效**：`InvokeFactory` 在 finally 解绑 api；改为扩展生命周期内常驻。
3. **事件结果被丢弃**：用了 `On<E>` 重载（返回 null），必须 `On<E,R>`；`{block:true}` 从未生效。
4. **`ctx.sessionManager` 空壳**：payload 里是 `"__pi_fn__"` 占位；改为宿主按需 `ctx.session.entries`。
5. **上下文急切读运行时动作**：`ThinkingLevel`/`Model`/`IsIdle` 在未绑定时抛错；改惰性 getter + try/catch。
6. **`fs.watch` 报 not a function**：改为明确「无后台事件循环」错误。

补充：事件序列化要注入 `type` + `toolName`（C# 记录把工具名编码在类型里，上游靠 `event.toolName` 分支）；
`pi.on` 的退订要真的调用 `On` 返回的 Action。

**测试方法（可复用）**：`tests/Pi.CodingAgent.Tests/JsExtensionRuntimeTests.cs` 用
`ExtensionLoader.CreateExtensionRuntime` + `LoadExtensionFromFactory` + `new ExtensionRunner(...)` +
`runner.BindCore(ExtensionActions, ExtensionContextActions)`，就能用**真实上游扩展**跑事件派发；
`runner.CreateCommandContext()` / `CreateToolContext()` 可注入命令与工具上下文。
语料探针（临时文件，已删）的结论：71 OK / 2 handler-fail（fs.watch、macOS osascript）/
7 load-fail（4 缺 npm 包、2 provider、1 测试脚本）/ 6 无默认导出。
