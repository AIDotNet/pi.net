## 续：`streaming-json.ts` 落地（`d17fdd9` / `fec56ff`）

`da412b039` 的前置。`src/Pi.Ai/Utils/StreamingJson.cs`：`StreamingJsonParser` + `ToolCallArgumentsStream`，32 例。

**关键设计决定**：值用 `object?` 树（`Dictionary`/`List`/`string`/`bool`/`double`/`null`），**不能用 `JsonNode`**
——快照共享是这个模块的核心（已完成子树在多个快照间共享），而 `System.Text.Json.Nodes` 不允许一个节点挂两个
父节点。`JsonObject` 只在 `Finish` 时由既有 `ParseToolCallArguments` 产出。已记为差异 C233。

**移植要点**：
- `snapshot()` 复制 open path（栈上容器逐个浅拷贝、自内向外串起来），共享已完成子树；拷贝信用 256 + 8/字符，
  `cost > credit` 时返回上一个快照（超大打开容器的预览会略微滞后，这是设计而非 bug）
- 待发标量（未结束的数字/字面量）需要单独一条分支：`cost` 多算 1，且 `copyOpenPath` 要把它塞进最内层副本
- `List` 的元素槽位在 `index == Count` 时是**追加**（`list[i] = v` 会越界）——`Place` 与 `SetSlot` 两处都要判
- 宽容语义：缺逗号/冒号容忍、位置非法的值丢弃、`\d` 之类非法转义留作字面文本、根值之后的文本忽略、从不抛出
- 32 层：`reportsInside = path.Count < 32`，更深者在关闭时整体上报一次
- 变更 `set`/`append` 在同一个 append 内可被后续字符延长（`open.change` 且是 `changes` 末条时才延长）

**验证口径**：期望值全部由上游 TS 实跑取得（临时副本去掉 `partial-json` 依赖后 node 跑探针，用完已删）。

**下一批（唯一剩余）**：把 provider 的 `toolcall_delta` 接到解析器，并让 `PartialChanges` 记住每个 content

## durable 遥测补齐（`526b702`）

- `phase.duration`：outcome 按上游规则算（terminal → done/aborted/faulted；waiting/sleeping；关闭或已结束 →
  aborted；其余 `next=<phase>`），错误状态 `task_faulted|failed|orphaned` + 500 字截断
- `tasks.active`：+1 三处在扫描/新建，-1 在终态块（`continue` 之前），关闭时对 `_live` 全量 -1（用 `wasClosing`
  防重复）
- `Invocation.Record`：提交观察者里跟随更新，必须在终态 `_live.Remove` **之前**赋值，否则 span 的 finally 读到 null

**`pi.durable.submit` 仍缺**，三条硬障碍（台账 §7.5）：受理只返回 id 没有 `result` 状态；上游 `addLink({context})`
与端口 `AddLink(StoredSpanLink)` 形状不一致；entry/submission 事件要穿透 `AdmitSubmissionAsync`。
硬填 `result="queued"` 就是假数据，所以停在能如实落地的地方。

## `pi.durable.submit` span（`e81f65b`）——一条「伪障碍」的教训

我上轮把「受理没有 result 状态」当成硬障碍。实际一读代码：`Admission.AdmitSubmissionAsync` 内部
`CreateSubmissionAsync(Status = Queued/Placed/Done/Unanswered)` 全都有，只是**没返回**。改成返回
`AdmissionResult(Id, Status)` 后，状态里唯一需要推导的是「边界放置后是 placed 还是 queued」——按
`applied.Users` 是否包含本次受理判断，不是猜。

**判断标准**：说「缺数据」之前先 grep 一眼那个数据是不是已经算出来只是被丢掉了。我这次差点又用「不硬接」把
可以忠实落地的东西挡在门外。

**设计对齐**：`SubmitAsync` 的 span 覆盖它的提交，`AdmitInCommitAsync` 只包受理——与上游
「public admission / admission only」的区分一致。

**仍缺两条**（真障碍）：link（上游 `addLink({context})`，端口 `AddLink(StoredSpanLink)` 收 trace/span id，
要等价得知适配器 carrier 键名）、`entry`/`submission` 事件（要把 span 穿透 `AdmitSubmissionAsync`）。

验证：`Pi.Durable.Tests` 576 全绿；`Pi.slnx` 0 警告 0 错误。

## durable 遥测收口（`7c5c9a2`）：link 与两个事件

**AddLink 形状（C235）**：端口原来收 `StoredSpanLink(traceId, spanId)`——那是**存储态**，让调用方自己拼 id，
等于把适配器细节泄漏出去。对齐上游后收 `SpanLink(ITelemetryContext, SpanAttributes?)`，`InMemorySpan` 用
`_carriers` 自解。这条是我前面几轮一直绕不过去的真障碍，根因是接口形状，不是 durable。

**事件位置的关键发现**：上游 `pi.durable.entry`/`pi.durable.submission` **不在受理里发**，而在
`Session.#publish` 按 `StorageWrite` 类型发，挂在「上下文携带的 span」上。我一开始以为是受理内部要穿透传参，
又是一次「想当然」。

**测试教训**：断言写成「每个 phase span 都要有 entry 事件」是错的——`prepare` 阶段不提交条目。
正确断言是「至少一个 span 有」。诊断时用 `Assert.True(false, string.Join(...))` 把事件名打出来比猜快得多。

验证：`Pi.Durable.Tests` 576（睡/唤醒 1 例并行噪声，单跑 12/12 绿）；`Pi.Telemetry.Tests` 30；`Pi.slnx` 0 警告 0 错误。

## `pi.durable.checkpoint` 与 `replay`（`055e267`）

- **checkpoint** ✅：`RuntimeImpl.CommitAsync` 里比较提交前后的 phase（`next is { Status: Running }` 且 phase 变了），
  事件挂 `invocation.Context` 的 span。上游就在 `runtime.commit` 里发，位置一致。
- **replay** ⛔：上游在 `tool.ts:963`，嵌套工具**命中已存结果**时发。端口的嵌套调用只有
  `Pi.CodingAgent/Core/NestedToolCalls.cs` 的 `NestedCallRecorder`（只记录、不重放），没有「从存储结果重放」的路径。
  `tool.ts` 1146 行、v1.4.0 就有，端口 durable 层没有对应 `runtime.tools` 面。

**判定口径**：`replay` 不是遥测漏接，是嵌套调用重放这个功能本身没移植。写进 §7.6，不硬造事件。

durable 遥测词表现在：reports/phase/phase.duration/tasks.active/submit/entry/submission/report/checkpoint 全接，
只剩 replay（功能缺口）。

## 端到端用例通过（`ebd3c95`）：嵌套调用真的能重放

`NestedToolCallTests` 用真实 harness（`OpenChatAsync` + `ScriptedProvider` + 装扩展）跑一轮工具调用：

**抓到一个只有端到端才暴露的 bug**：`StartNestedAsync` 里比较「同工具同参数」时直接比
